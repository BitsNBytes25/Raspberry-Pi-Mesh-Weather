# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [NEXT] - YYYY-MM-DD

### Added

- **Sunrise/sunset via OpenWeatherMap** (`open_weather_map.py`) — `get_current_conditions()` now also normalizes the API's `sys.sunrise` and `sys.sunset` (epoch seconds, local time for the location) into its returned dict, reusing the existing cached fetch so there is no extra network call.
- **`sun` getters** (`libs/sun.py`) — `get_sunrise()` and `get_sunset()` return the OWM epoch timestamps, and `get_next_sun_event(now=None)` returns `{'name': 'sunrise'|'sunset', 'dt': epoch}` for the first event after `now` (pre-dawn → sunrise, daytime → sunset; `None` when both have passed or data is unavailable). `format_time(ts)` renders a short local time-of-day string (e.g. `8:18 PM`).
- **`sun` command** — New direct-message `sun` and channel `!sun` command reporting today's sunrise and sunset, each with its clock time and a relative label against now (e.g. `Sunset 10:18 PM (in 1h 19m)` / `Sunrise 12:13 PM (8h 46m ago)`). Sun events are service-only (no local sensor), so this is always service-derived; missing values are omitted and all-`None` yields a "no sunrise/sunset available" response.
- **`all` command sunrise/sunset** — The `all` command now appends the *next* sun event only as a trailing pipe item (e.g. `… | sunset 10:18 PM`), so daytime shows the upcoming sunset, pre-dawn the upcoming sunrise, and the evening shows nothing once today's sunset has passed.
- **Sunrise/sunset tests** — New `test_sun.py` covering the getters, `get_next_sun_event` (daytime/pre-dawn/evening/no-data) and `format_time`; `test_commands.py` adds `sun` command tests and `all`-command tests for the sun item; `test_open_weather_map.py` expectations updated for the new `sunrise`/`sunset` keys.
- **NWS alert filtering** (`weather_alerts.py`) — Replaced the broad `NWS_EVENT_ICONS` keyword table with the tracked-value sets from `docs/weather_alert_keys.md`: `TRACKED_EVENTS` (the 43 tracked event types), `TRACKED_SEVERITIES` (Extreme/Severe), `TRACKED_URGENCIES` (Immediate/Expected) and `TRACKED_CERTAINTIES` (Observed/Likely). `get_alerts()` now returns a list of `{icon, title, id, expiration}` records for alerts that satisfy **all four** checks; anything else is ignored. Event-to-icon resolution is now an exact per-tracked-event match (`EVENT_ICONS`) resolved through `get_icon()` and the active `icon_style`.
- **`get_new_alerts()`** (`weather_alerts.py`) — In-memory dedup for alert broadcasts. Keeps a map of alert id → expiration of already-sent alerts, drops expired ids so memory stays bounded in the long-running process, and returns only alerts not yet broadcast. First call returns everything currently active; subsequent calls return only what is new.
- **`!alerts` command** — Consumes `get_new_alerts()` (rather than `get_alerts`) and assembles each `{icon}  {title}` line, so the 30-minute radio auto-broadcast no longer repeats an alert it has already sent.
- **Alert tests** — `test_weather_alerts.py` reworked for exact per-event icon matching, the dict-shaped `get_alerts()` return, untracked fixtures now expected empty, and `get_new_alerts()` first/mixed/expired-prune behavior. Added `severe_tornado_warning.json` and `severe_thunderstorm_warning.json` fixtures for tracked-event coverage.
- **`ScheduledTasks` service** (`services/scheduled_tasks.py`) — Centralized, radio-agnostic scheduler for recurring mesh jobs. It takes a mesh radio as its sender and broadcasts each task's result via the radio's new `broadcast(text)` method, so the job logic (windowed scheduling, hourly interval, retry-on-failure) is written once and works with both MeshCore and Meshtastic. Currently only the daily forecast is scheduled, broadcasting in the 5–9 AM and 4–6 PM windows (at most hourly, retrying on failure, silent outside its window); this service is the home for the future hourly jobs (current weather during the day, sunrise/sunset, ...). A `clock` parameter lets the scheduling be driven by an injectable clock for testing.
- **`broadcast(text)` on each radio** (`services/radios/meshcore_radio`, `meshtastic_radio`) — New async transmit adapter exposed for the scheduled tasks service: MeshCore sends to the weather channel, Meshtastic sends to the default channel. The previously inlined `run_daily_forecast()` and its window/interval scheduling have been removed from each radio's `run()` loop, which now handles only the radio-specific work (adverts, alerts, contact sync).
- **`ScheduledTasks` unit tests** — Covering `run_daily_forecast()` success/failure/missing-command/no-data paths, the forecast window check, the hourly due check, and the run loop (broadcasts in-window, stays silent out-of-window, respects the hourly interval, and retries after a failed attempt), using an injectable clock and a patched `asyncio.sleep`.
- **Alert auto-broadcast moved to `ScheduledTasks`** — The per-radio `run_alerts()` auto-broadcast (and its 30-minute `ALERT_INTERVAL`) is now a shared job in the `ScheduledTasks` subsystem, run via each radio's `broadcast(text)` adapter. Alerts are now checked every 5 minutes (the radios' 30-minute cadence was too long for emergency events and a per-minute check too frequent for the API). In the tick loop the alert check runs first: if an alert is broadcast, the tick's `sent` flag is set, which suppresses the in-window forecast/current-weather job for that tick (so the at-most-one-broadcast-per-tick guarantee still holds and the preempted job simply retries on the next tick, at most a minute later). The alert check still respects its own 5-minute interval gate and retries on failure.
- **Alert preemption and interval tests** (`test_scheduled_tasks.py`) — New tests cover `run_alerts()` success/missing/error/no-data paths and the 5-minute gate, plus the run loop: an alert broadcast preempts the in-window forecast *and* the in-window current-weather for that tick, a failed/no-alert check still lets the in-window job run, the forecast retry-on-failure path, and the alert retry on the next due tick.
- **OpenWeatherMap wind lookup** — `get_current_conditions()` now also normalizes the API `wind` block into `wind_speed`, `wind_deg` and `wind_gust` (metric: m/s, degrees), so the wind data comes from the same single cached current-conditions fetch as the other readings.
- **`wind` command** — New direct-message `wind` and channel `!wind` command reporting the current wind from the OpenWeatherMap service: speed in m/s, gust in m/s, and direction as a 16-point compass shorthand (e.g. `NNW`). There is no local wind sensor, so this is always service-derived.
- **`all` command** — Now includes the current wind speed and direction (e.g. `… | 4.5 m/s wind NNW`) alongside temperature, humidity and pressure.
- **Wind compass shorthand** (`libs/wind.py`) — `get_wind_compass()` converts the OWM wind bearing to a 16-point compass name.
- **OpenWeatherMap current-conditions fallback** — New `OpenWeatherMap.get_current_conditions()` fetches the `/data/2.5/weather` current-conditions lookup (metric units) for the configured location and caches the result in memory for 300 s, including failures so a downed network is not re-pounded within the window. A shared process-wide accessor (`open_weather_map.get_current_conditions()`) is used by the `get_temperature()`, `get_pressure()` and `get_humidity()` getters so a single command that reads all three triggers at most one OpenWeatherMap call. When the local sensor reading is unavailable (`state.get(...) is None`), each getter falls back to the matching current-conditions value — temperature/humidity in °C/% and pressure as the `sea_level` (hPa) field to match the BME280's mean-sea-level reading — and returns `None` if both the sensor and the service are unavailable, so the commands still emit their normal "no data" responses. The `temp`, `pres`, `humid` and `all` commands, the SH1106 display, and Home Assistant therefore all degrade gracefully to OpenWeatherMap when the local sensor is down. A 5 s request timeout was also added to `_fetch_data` so a hung connection cannot block the event loop.
- **`humidity` command** — The full `humidity` command is now supported as a direct message command and as `!humidity` on the weather channel, alongside the existing `humid` shorthand. Both resolve to the same response. The `--test` daemon command list now includes `humidity` as well.
- **`temp` command tests** — Unit tests covering the no-temperature and no-humidity paths and every temperature band (freezing, cold, chilly, comfortable, warm, hot, oppressive), including the dry-air descriptions in the 18–24°C band.
- **Heat index tests** — Unit tests for `get_heat_index`, including the sub-26.7°C applicability threshold and known values.
- **`weather_forecast` tests** — Unit tests for `WeatherForecast`: init validation (missing API key / missing location), `get_daily_forecast` against the Columbus fixture (including the no-today-match fallback, request-failure, and malformed-response paths), and `get_description` period-window logic.
- **Icon map library** (`libs/icon_map.py`) — Centralised icon lookup keyed by standard, source-independent icon names (`sun`, `moon`, `cloud`, `rain`, `drizzle`, `snow`, `fog`, `thunderstorm`, `sun_clouds`) rather than any feed's codes. Two glyph sets are available: `WEATHER_ICONS_MODERN` (colour emoji, best on modern clients) and `WEATHER_ICONS_COMPATIBLE` (basic U+2600-U+27BF block glyphs, safe on the limited fonts of ESP32/NRF mesh devices). The internal `OWM_ICON_NAMES` map translates OpenWeatherMap codes to standard names, and `get_weather_icon(owm_code)` / `get_icon(name)` resolve a code or name via the new `general.icon_style` config option, so callers never need to know which set or which feed is active. Covers all WMO codes, including the previously-missing 45/48 (mist/frost), 80/81 (snow showers) and 95/96/99 (thunderstorm) codes.
- **`icons` command** — A minimal direct-message diagnostic that returns every weather glyph of the currently configured icon style (via `icon_map.get_icon`) in a fixed order, so the sender can verify which icons render on their device. Response is a single short line (≤ 17 characters compatible, ≤ 26 modern) and always fits the 130/200-character mesh limits.
- **`freezing` icon** (`icon_map.py`) — New standard icon name for sub-1°C conditions. Modern set: `🥶️` (Ice Face, U+1F976 + VS). Compatible set: `❄❄` (U+2744 × 2, double snowflake to distinguish from the single-snowflake `snow` glyph). Included in `STANDARD_ICON_NAMES` so the `icons` diagnostic now shows 10 glyphs.
- Current conditions (via `!all`) are sent during the daytime

### Changed

- **Alert icons** — `weather_alerts.py`'s hard-coded emoji table is gone: NWS event keywords now map to standard icon names (`cyclone`, `flood`, `heat`, `wind`, `dust`, `mask`, `fire`, `avalanche`, `surf`, `ship`, `info`, `warning` — all new `STANDARD_ICON_NAMES` in `libs/icon_map.py`, added to both glyph sets), and `get_alerts()` resolves them via `get_icon()`. `!alerts` now follows the active `general.icon_style` like the forecast icons (colour emoji with `modern`, basic symbols with `compatible`); the keyword → standard-name resolution stays local to `weather_alerts.py`. `test_weather_alerts.py` added, covering keyword resolution and the existing `tests/fixtures/api_weather_gov/` fixtures.
- **`forecast` command** — Now shows a rolling forecast of the next entries in chronological order (starting from now) instead of a fixed "today" summary, so an evening call starts with the current evening and spills into tomorrow. `get_daily_forecast` returns a list of normalized entries (dt/hour/date/temp/feels_like/humidity/pop/description/icon); the narrative `get_description` and its period-window logic were removed. Entries are 3-hour buckets, so each is labelled by its actual clock time (e.g. "6:00 PM"), with a "Tomorrow" prefix for entries on the next day.
- **`forecast` command** — Output reformatted as a compact two-state summary to cut characters: a one-line narrative (e.g. "Light rain until 7 AM, then broken clouds") appears on the header line, followed by the current and change slots as `icon time: temp` (e.g. "🌧️ 10 PM: 7.0°C/45°F"). When skies are calm and precipitation is arriving, the narrative leads with the incoming weather ("Light rain around 7 AM"). The per-entry listing and the "Low/High" min/max line were removed.
- **`forecast` command** — Summary now describes a single weather state instead of two ("X until N then Y"): "Light rain until 3A" (active now, ending at the next change), "Light rain around 7A" (calm now, with active weather arriving), or just the state alone (single-state window, or no active weather — calm cloud-cover states are skipped). The per-entry `icon time: temp` listing is unchanged.
- **`all` command** output reformatted to be cleaner
- **`all` command** — Replaced hardcoded emoji in `_weather_icon` with `icon_map.get_icon()` lookups keyed by standard names (`freezing`, `rain`, `sun`, `sun_clouds`). The icon shown now respects the active `general.icon_style` (compatible by default) rather than always using colour emoji.
- **`temp` command** — Replaced hardcoded emoji in `cmd_temp()` with `icon_map.get_icon()` lookups keyed by standard names (`freezing`, `snow`, `rain`, `cloud`, `sun`, `heat`, `fire`), so the leading icon in each temperature band now respects the active `general.icon_style` (compatible by default) rather than always using colour emoji. The `temp_` assertions in `test_commands.py` now build the expected glyph via `icon_map.get_icon()` so they pass under either style.
- **Test fixes** — `test_icon_map` and `test_commands` updated to match the actual compatible glyph set (moon `🌙️` U+1F319, sun_clouds `☀`, drizzle `☔` U+2614, thunderstorm `⚡` U+26A1) and to cover the new `freezing` glyph. Broadened the `test_compatible_glyphs_are_widely_supported` range to permit the moon emoji codepoint and the VS character.
- **`temp` command** — Fixed a malformed oppressive-heat message (missing closing parenthesis) and a missing period at the end of the >29°C storm warning.
- **`temp` command** — Fixed the 18–24°C band falling through to a bare temperature readout when humidity is below 30%; added dry-air descriptions for that case instead.
- **`temp` command** — Switched from truncated (`int`) to rounded values for display and band selection so borderline temperatures (e.g. 24.9°C) get the correct description.
- **`temp` command** — Added a muggy (high-humidity) description to the 24–29°C band for temperatures where the heat index is not yet in the "limit activity" range.
- Cleanup output when running `daemon --test` to better view raw command responses
- **Commands refactored into `commands/` package** — The monolithic `libs/commands.py` was split into the `libs/commands/` package with one module per command (`help`, `ping`, `uptime`, `cpu`, `temp`, `pres`, `humidity`, `all_sensors`, `forecast`, `alerts`, `reboot`, `wake`, `net`) plus a separate `handler.py` holding the common functionality: the command registry, the `command()` decorator, the response classes, and the `get_command()` dispatch.
- **Command authorization now enforced** — The registry previously stored the raw command functions, so `get_command()` returned them unwrapped and the `auth` guard was bypassed, letting any radio run protected commands. The `handler` now stores the auth-wrapping function, so dispatch enforces the `auth` flag against the caller's public key; unauthorized callers (or a missing/empty key) get a "not authorized" response. `reboot`, `net`, and `wake` are now genuinely protected.
- **`ping` command** — No longer raises `TypeError` when invoked with no target (the channel/internal path calls commands with `None`); returns a bare `pong` instead of a crash.
- **Weather icons** — Forecast icons are now resolved through `get_weather_icon()` from the new `general.icon_style` setting, defaulting to the `compatible` glyph set so icons render on mesh clients instead of showing as "*". Colour emoji are still available by setting `icon_style: "modern"`.
- **`icon_map`** — `STANDARD_ICON_NAMES` is now an ordered list (authoritative, single source of truth) instead of an unordered set, giving consumers a stable, deterministic glyph sequence. The `icons` command reuses this list directly rather than declaring its own.
- **`open_weather_map` module** — Renamed `weather_forecast` (`WeatherForecast`) to `open_weather_map` (`OpenWeatherMap`) so it is a dedicated OpenWeatherMap client ready for additional lookups (current weather, city lookup, etc.). `get_daily_forecast` behavior is unchanged.
- **Pressure trend only reported from local sensor data** — `get_pressure_change()` now returns a `float` (1.0 / 0.0 / -1.0) when local pressure history is present and `None` when it is not (e.g. no BME280 attached, so only the hosted OpenWeatherMap value is available). The `pres`, `all` and `temp` commands now omit the trend (`rising` / `falling` / `stable`) when it is `None`: `pres` reports just the basic pressure, `all` drops the `(…)` trend suffix, and the 18–24°C `temp` band falls back to its plain comfort message. A hosted OpenWeatherMap pressure value is therefore never mis-labelled as "stable". New library and command tests cover the `None` path.
- **Forecast broadcast schedule** — The scheduled forecast broadcast now runs every hour between 5 and 9 AM and again between 4 and 6 PM (previously once daily between 6 and 7 AM). Gated by a new `FORECAST_INTERVAL` (1 h) rather than `FLOOD_INTERVAL`, so the flood and local advert cadences are unchanged.

## [1.0.0] - 2026-06-20

### Added

- **Environmental sensor tracking** — Pulls temperature, pressure, and humidity from locally-attached sensors and supports the **BME280**.
- **Mesh radio support** — Sends data, forecasts, and alerts over the mesh network and receives commands and queries:
  - **MeshCore**: listens on the `#weather` channel and responds with current weather data; direct messages also supported.
  - **Meshtastic**: listens on any configured channel for group messages.
  - Weather channel commands: `!temperature`, `!humidity`, `!pressure`, `!all`, `!forecast`, `!alerts`.
  - Direct message commands: `help`, `temperature`, `humidity`, `pressure`, `ping`, `uptime`, `cpu`, `wake`, `forecast`, `alerts`.
  - Administrative (authorized) commands: `reboot`, `net` (MeshCore only, via `auth_radios`).
- **Forecast and alerts** — Fetches a 1-day forecast and current weather alerts from OpenWeatherMap / NWS for mesh broadcast, with altitude-adjusted pressure readings (MSLP).
- **Home Assistant integration** — Uploads sensor metrics and discovered radios to a local Home Assistant installation, including optional custom device icons.
- **OLED display** — Displays basic diagnostic information on an attached display; send `wake` over the mesh to light the display for 2 minutes.
  - Supports the Microcenter OLED Display (345785).
- **MQTT packet capture** — Acts as a mesh observer by uploading raw packets to MQTT servers (multiple brokers supported, each with its own authentication, WebSocket, TLS, and MeshCore token auth options).
- **`config.yaml` configuration** — All features are optional and enabled/disabled via configuration, covering display, radio, sensors, location, weather, Home Assistant, security, and MQTT settings.
- **Modular installation** — Dependencies are installed per enabled hardware feature group (`radio-meshcore`, `radio-meshtastic`, `sensor-bme280`, `display-sh1106`) via `install.sh` / `uv sync`, so only what you use is installed.
- **Test suite** — Unit tests using pytest (with pytest-asyncio, pytest-mock, and pytest-cov).
- **`daemon` entry point** — A single systemd-managed daemon with `--debug` and `--test` modes.
- **License** — AGPLv3.

### Noted

- Currently only **serial/USB connected radios** are supported.
- Hardware features load lazily; the daemon starts on a machine without the full hardware stack attached (missing hardware is logged as an error).
- When enabling or disabling a feature, re-run `install.sh` (or `uv sync` with the matching group) so dependencies match the configuration.
